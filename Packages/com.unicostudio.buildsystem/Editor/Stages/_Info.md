# Build Stages

The ordered `IBuildStage` pipeline. `UnicoBuildService.Advance` runs them from the saved step index; any stage may trigger a domain reload and be resumed.

Order (built by `UnicoBuildService.Stages`):
1. `ApplyVersionStage` — writes `PlayerSettings.bundleVersion` from the request; bumps the platform build code (`BuildVersioning`, `+1`) when requested; bumps `AddressablesVersionStore.Version` (`+1`) when requested.
2. `ConfigureDefinesStage` — resolves the define delta via `BuildDefineResolver`: the config's `ExtraDefines`/`StripDefines` (self-loaded via `BuildConfigCatalog`, read exactly once — the stage never re-runs after the reload it may trigger) merged with the test-mode kind rule (`BuildSystemSettings.ResolveTestModeDefine()`). Config `ExtraDefines` are MERGED into `ctx.ExtraScriptingDefines` via `ApplyExtraDefines` — never assigned over it, since a PreBuild hook may already have contributed defines there (applied at build time, no reload; the player build only — the editor and the Addressables build do not see them). The kind rule's global add and every `StripDefines`/Release removal go through `NextGlobalDefines` into ONE `SetScriptingDefineSymbols` call (domain reload → resumer continues at the next step), undone by the snapshot restore in `Finish`. The write is skipped entirely when the resulting define set equals the current one, so an already-matching target costs no reload.
3. `AddressablesStage` (only if `BuildAddressables`) — switches the active profile (enum→name at the API boundary; throws if the profile is missing), then calls `AddressablesRuntimeProperties.ClearCachedPropertyValues()` before it arms the guard and before it evaluates any profile variable. That cache is domain-lifetime and the only thing that clears it is Addressables' own `BuildScriptBase.BuildData`, which runs AFTER this stage validates — so without the clear, a value warmed earlier in the session (by `ApplyVersionStage` bumping the store, or by `RemotePathCheck` running on every panel repaint) would be validated here, then re-evaluated by `BuildData`, fail, and — the evaluator swallows failures — bake the raw token text into the shipped catalog as the remote URL. Clearing here is what makes this stage's validation and the catalog write see the same state. It then arms `ContentStateGuard` before any content operation: resolve the content-state path via `ContentUpdateScript.GetContentStateDataPath(false)`, then one of THREE outcomes — (a) Addressables reports the path is remote (`ShouldPathUseWebRequest`) ⇒ nothing is armed at all, and the step log records why: a URL cannot be copied, and a record that could never restore anything is worse than none; (b) a local path whose file already exists ⇒ copy it to `Library/UnicoBuild/content_state_backup_{platform}.bin` and arm with `existedBefore: true` (a failed copy degrades to an empty backup path plus a warning, never a failed build); (c) a local path whose file does not exist yet ⇒ arm with `existedBefore: false` and an empty backup path, which is what lets a failed FIRST New Build delete the content-state file it created instead of leaving one that describes a build that never shipped. The record carries the running job's `BuildJobState.StartedTicksUtc`, so only that job's `Finish` — or crash recovery, via `AnyJobStamp` — can apply it. That order is load-bearing — the resolver evaluates through the ACTIVE profile, so arming before the switch would resolve the developer's profile, and arming after the steps below would be after the file is already overwritten. It then evaluates `Remote.BuildPath` and `Remote.LoadPath` and refuses to build on a binding that did not resolve — an unresolved binding would bake a garbage URL into the catalog, since the evaluator substitutes the token's own text rather than throwing. THE GUARD NO LONGER NAMES A HOST CLASS: the verdict comes from `ProfileBindingRule.Inspect`, the same method preflight's `RemotePathCheck` acts on, so the two can never disagree about what counts as broken (only the wording is local). It then cleans player content and runs Update-Previous or a New Build per `AddressablesMode`. Update-Previous mirrors the Groups window's 2.x menu flow (`LoadContentState` → `PreviousContentState` on an `AddressablesDataBuilderInput` → active builder), NOT the legacy `ContentUpdateScript.BuildContentUpdate` API: the legacy path hard-requires catalog-path equality, which this project's catalog-pinned layout (catalog stays at the original player's path — e.g. `v5/Production` — while new bundles land in the current `v{N}` folder) intentionally violates. Bumping VERSION_NO + Update Previous is therefore a VALID, normal flow. The menu's "Check for Update Restrictions" option is honored batch-style (non-Disabled + modified restricted entries ⇒ fail with the list). The Addressables builders never throw: a NULL result or non-empty `result.Error` fails the stage via `BuildFailedException` — a swallowed error would ship a player without its remote content. Entire body is gated by `UNICO_HAS_ADDRESSABLES`; without the package the stub `Execute` throws `BuildFailedException`.
4. `PlayerBuildStage` (only if `BuildPlayer`) — runs `BuildPipeline.BuildPlayer`. iOS emits an Xcode project; Android emits APK then/or AAB per `OutputKind`. Applies `ctx.ExtraScriptingDefines` via `BuildPlayerOptions`. Generates Android debug symbols (`DebugSymbols.level = SymbolTable`) only for the AAB, and surfaces the uploadable archive by ASKING THE BUILD'S OWN REPORT — `report.GetFiles()` entries with role `"Symbols"` (measured on a real 6000.0.62f1 AAB: exactly one, at its output-folder path), filtered through the pure, tested `SelectSymbolsArchives`. This replaced the `*.symbols.zip` glob over the output folder, which reconstructed Unity's naming and needed an mtime filter to avoid adopting an earlier build's archive; the `.symbols.zip` suffix survives only as a guard on API-returned values, so a future Unity classifying something else under `"Symbols"` is skipped rather than mislabeled. Maps `BuildRequest.Compression` to `BuildOptions` flags (`OptionsFor`) — scripted builds ignore the Build Settings window's Compression Method, so without these flags the artifact would silently ship with Default compression. It knows nothing about any metadata-exporting tool: surfacing a tracker's build-info file is HOST GLUE (a `[UnicoBuildStep(PostSuccess)]` step in the game's `Assets/`, calling the tool's own path API and `UnicoBuildService.AppendPostArtifact`) — the stage used to reconstruct that tool's filename convention here, which is exactly what the boundary program's acceptance criterion forbids.

Rules:
- Every stage receives the same `BuildContext`; report progress via `ctx.AddStep(...)` and outputs via `ctx.AddArtifact(...)`. Both are persisted after each stage and survive reloads.
- Changing a define globally forces a reload — only `ConfigureDefinesStage` may touch global defines, and only for the test-mode kind rule (both directions) and `StripDefines`. Everything else additive uses `ctx.ExtraScriptingDefines`. The kind rule is the deliberate exception to "additive means player-only": editor assemblies compile with the active target's global defines, so anything the build's own editor-side participants must see has to be global.
- Stages must be safe at the step boundary: `Advance` re-creates the stages and the context on each call, so a stage runs once per `StepIndex`; its side effects must not conflict with the already-applied earlier steps.
- Failures throw; `UnicoBuildService` catches, restores dev state, and records the failure. Do not swallow build errors inside a stage.
- The default output folder (when the request leaves it empty) is `Builds/{Platform}/{Kind}/`.
