# Build UI

The single build control panel.

Contents:
- `BuildPanelWindow` — an `EditorWindow` opened from `UnicoStudio ▸ BuildPanel`. Presents the `BuildRequest` fields (in boxed, icon-headed sections since 0.13.0), live pre-flight results, an artifact-name preview, and the Build button.
- `PanelDecisions` — the panel's pure/testable surface (0.13.0): version-row gating (which bump rows are enabled AND their force-false effective values), the pinned editor-icon name set, `FormatStartedLocal` for the result header stamp, and `AccentFor` (kind → background tint). Every decision a test can pin lives here; the window stays IMGUI plumbing.

Rules:
- Presentation only. The panel assembles a `BuildRequest`, renders the pre-flight results (from a once-built `PreflightRunner.Default()` set cached in a static field), and hands off to `UnicoBuildService.Start`. It must not run build stages, mutate defines, or touch Addressables directly.
- Passing pre-flight checks render as ONE compact line ("✓ N/M checks passed") with a details foldout; only Warn/Block results get full HelpBoxes. The foldout state is deliberately non-serialized (kept out of the Undo stack, collapses after reloads).
- The Build button is disabled while `UnicoBuildService.IsRunning` and when the request selects no stage (both Build Addressables and Build Player off). A `Block` pre-flight result stops the click with a dialog; any `Warn` results require one explicit acknowledgement dialog (listing every warning) before `Start` — this is the safety gate that replaces the suppressed `UnicoBuildPreprocessor` modals. A needed platform switch is folded into that dialog ("Switch & Build"). While a job is running the panel offers a confirm-gated "Reset stuck job" button (`UnicoBuildService.ResetStuckJob`) for wedged jobs.
- Read-only context (current build code, current Addressables version) is displayed but never editable; the `AddressablesVersionStore` is loaded once and cached in a field (a missing store shows "unavailable" — no per-event `AssetDatabase` load or exception-as-control-flow).
- The active-vs-target platform-switch warning is rendered once by `PlatformMatchCheck` in the pre-flight results — the panel does not add a second inline HelpBox for it.
- The artifact preview must use the same `BuildArtifactNaming.FileName` the stages use, so what the user sees matches the output.
- Field labels + tooltips are cached `GUIContent` in the nested `Tips` class (no per-`OnGUI` allocation); update the tooltip there when a field's behavior changes. Multi-part tooltips separate their parts with `\n`, not run-on spacing.
- Player-only fields (compression, output toggles, label, output folder) are greyed via `DisabledScope(!BuildPlayer)`, mirroring how Addressables Mode follows Build Addressables. The artifact-name preview renders right above the Build button (the last thing read before committing) and only for player builds.
- Version-row gating (0.13.0): `VersionName` is deliberately ALWAYS editable — `ApplyVersionStage` runs unconditionally in every job (measured; content-only jobs stamp the version too). The bump toggles are gated by the stage that gives them meaning (`BumpBuildCode` ↔ Build Player, `BumpAddressables` ↔ Build Addressables), and their effective values are FORCED false at the top of `OnGUI` via `PanelDecisions.GateVersionRows`, before the preflight run — a greyed row must never smuggle a hidden true into `Start()`. Same force-false rule the Addressables-absent branch already applied. `BumpConsistencyCheck` stays registered for the CLI, which has no UI.
- Sections are boxed (`EditorStyles.helpBox`) with icon headers; the window consumes the named `PanelDecisions.Icon*` CONSTANTS (never string literals), `IconNames` aggregates those same constants, and the pinning test resolves each one on the running Unity version — so what the test covers is by construction what the window renders (`IconContent` degrades to an empty content on an unknown name; an unasserted name would ship as an invisible hole). Base names only, no `d_` prefix: `IconContent` auto-selects the skin variant, and a hardcoded dark-skin glyph is near-invisible on the light skin. The Target box header shows the platform icon.
- Kind accent (0.13.0): the Target box background and the Build button are tinted by `PanelDecisions.AccentFor` (Test → green, Release → orange, muted). Color is never the sole carrier — the kind name stays in the popup and dialogs. Per-user off-switch: window-tab context menu → "Accent Colors" (`EditorPrefs` key `UnicoBuild.Panel.AccentColors`, default on; personal preference, deliberately NOT project data).
- The Target box shows which `BuildTargetConfig` the request resolves ("Config: <asset name>" or the fallback note) via a log-free `FirstOrDefault` — NOT `BuildConfigCatalog.Find`, whose duplicate complaint is a `LogError` and this line renders every repaint. `ConfigPresenceCheck` owns the messaging; the row only mirrors the resolution. The window itself calls `BuildConfigCatalog.LoadAll` once per `OnGUI` pass (shared by this row and `ResolveProfile`); config-reading checks still run their own discovery inside the preflight pass, and `ResolveProfile`/those checks can still log on a duplicated config — only this ROW is log-free.
- The result header carries a `TestPassed`/`TestFailed` icon, the duration, and the run's start stamp (`PanelDecisions.FormatStartedLocal`; legacy results without `StartedUtc` simply omit it).
- The form (`_req`) is `[SerializeField]` on the window: it survives domain reloads and is undo-enabled via `Undo.RecordObject(this)` taken BEFORE the widgets, but ONLY on events that can mutate the form (mouse, key, drag-perform, and `ExecuteCommand` other than `UndoRedoPerformed`). Never record on every event: Layout/Repaint passes — including the ones the undo system triggers while restoring — would re-record the state a Ctrl+Z just restored, so undo could never leave the panel and each record would clear the redo stack. Undo/redo drops text focus + repaints via `undoRedoPerformed`. This is entirely a window concern — `BuildRequest` and the core stay untouched.
- An empty output folder is valid and means the default `Builds/{Platform}/{Kind}/` — shown as an in-field placeholder hint.
